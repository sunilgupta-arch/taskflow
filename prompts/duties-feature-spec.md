# Store Duties — Feature Spec

Portal-side (CLIENT) feature. The client owns a store, has a fixed set of recurring duties
(see [arden-counter-duties.md](arden-counter-duties.md)), assigns them to store employees per
day, and wants to know how long each employee actually takes.

Replaces a paper checklist. Built 2026-08-10.

## Decisions

| Question | Decision |
|---|---|
| Scheduling | **Both** — a duty can carry recurrence rules that auto-generate dated rows, and an admin can add/remove one-off assignments on any date |
| Who manages | **CLIENT_ADMIN + CLIENT_TOP_MGMT** — matches the existing portal "isAdmin" convention |
| Time tracking | **Single session** — Start → Finish, storing `started_at`, `completed_at`, `duration_seconds` |

## Scope

- Full CRUD on a duty catalogue
- Per-day, per-employee assignment via a date-driven schedule screen
- Employee self-service: see today's duties, Start, Finish
- Admin reporting: average/total time per duty, per employee, with comparison across employees

Out of scope for this pass: pause/resume, photo proof, mobile push, duty dependencies.

## Data model

Three tables. The split between **what a duty is** and **how it is managed** is deliberate:
a duty is raw text that can sit in the catalogue with nobody assigned, and the same duty can
be performed by different people on different days without duplicating the duty row.

```
store_duties          duty_schedules              duty_assignments
(WHAT)                (HOW it is managed)         (THE WORK)
  "Vacuum F1-F3"  →     Ravi,  weekly Thu     →     Thu 13 Aug · Ravi  · completed 00:14:02
                  →     Priya, weekly Fri     →     Fri 14 Aug · Priya · pending
                                                    Sat 15 Aug · Ravi  · pending  (manual, no rule)
```

Assignment rows are **materialized lazily on read** — nothing is generated by cron. When a date
is read, the model finds the active rules that apply and `INSERT IGNORE`s the rows. Self-healing,
no backfill job, no drift if the server was down.

### `store_duties` — the raw catalogue

| Column | Notes |
|---|---|
| `id`, `org_id` | |
| `title` | e.g. "Deep clean bathrooms, break room and stock room" |
| `description` | Optional longer instruction |
| `category` | Grouping label only — "Daily Duties", "Evening Closing", "Wednesday" |
| `estimated_minutes` | Optional target, used to flag overruns in the report |
| `sort_order` | Display order within a category |
| `is_active` | Soft delete — never hard-delete, history depends on it |
| `created_by` | Nullable; NULL for seeded rows |

No scheduling columns and no assignee. A duty with no rules never appears on anyone's day.

### `duty_schedules` — how a duty is managed

| Column | Notes |
|---|---|
| `duty_id` → `store_duties` | |
| `user_id` → `users` | Who performs it under this rule |
| `recurrence` | `once` \| `daily` \| `weekly` |
| `recurrence_days` | CSV weekday numbers, `0=Sun … 6=Sat` — same convention as `models/Task.js` and `ClientRequest.matchesDate` |
| `start_date`, `end_date` | Window; `end_date` nullable = open-ended |
| `is_active` | |

Zero or many rules per duty.

### `duty_assignments` — the actual work

| Column | Notes |
|---|---|
| `duty_id`, `user_id`, `duty_date` | |
| `schedule_id` | The rule that produced it; NULL when assigned by hand |
| `status` | `pending` \| `in_progress` \| `completed` \| `skipped` |
| `started_at`, `completed_at` | UTC |
| `duration_seconds` | `TIMESTAMPDIFF(SECOND, …)` on Finish. Seconds rather than the `duration_minutes` used elsewhere in the app — many store duties run under a minute and the whole point is comparing employees |
| `source` | `auto` \| `manual` |
| **`UNIQUE (duty_id, user_id, duty_date)`** | Makes materialization idempotent |

A duty removed from a single day becomes a **`skipped`** row, not a deleted one — otherwise
materialization would recreate it on the next read.

Deleting a rule removes only *future unstarted* work. Completed history survives.

## Permissions

| Action | Roles |
|---|---|
| Duty CRUD, schedule rules, assign, view all, reports | `CLIENT_ADMIN`, `CLIENT_TOP_MGMT` |
| View own duties, Start, Finish | Any `CLIENT_*` role |

Enforced with `requireRoles(...)` in `portal/routes/portal.js`, plus an ownership check in the
controller so an employee cannot start someone else's duty.

## Routes — all under `/portal`

```text
GET    /duties                                       Page shell (section: 'duties')

# My duties — any client role
GET    /duties/mine?date=YYYY-MM-DD
POST   /duties/assignments/:id/start
POST   /duties/assignments/:id/finish

# Catalogue — the raw duty only (admin)
GET    /duties/catalogue
POST   /duties/catalogue
PUT    /duties/catalogue/:id
DELETE /duties/catalogue/:id                         Soft archive

# Schedule rules (admin)
GET    /duties/catalogue/:id/schedules
POST   /duties/catalogue/:id/schedules
DELETE /duties/catalogue/:id/schedules/:scheduleId

# Day schedule + reporting (admin)
GET    /duties/schedule?date=
GET    /duties/report?from=&to=
POST   /duties/assignments                           Manual one-off assignment
DELETE /duties/assignments/:id                       Skip for that day
```

## UI — `portal/views/portal/duties.ejs`

One page, tabbed. Admin sees four tabs; everyone else sees only the first.

1. **My Duties** — date picker (defaults today), grouped by category, each row has a live
   running timer and a Start/Finish button. Completed rows show elapsed time.
2. **Schedule** *(admin)* — pick a date, see every employee as a block of duty chips, assign
   from a dropdown, remove with an ×.
3. **Catalogue** *(admin)* — every duty with its rules listed inline ("Ravi · Thu", "Priya · Fri")
   or "Not scheduled". A calendar button per row opens the rules modal; a duty modal edits only
   title/description/category/target/sort.
4. **Report** *(admin)* — date range → duty × employee with runs, average, fastest, slowest,
   and an overrun flag against `estimated_minutes`.

Follows portal conventions: Bootstrap 5, `--tf-*` theme variables, one inline `<script>` block
of plain global functions, `ApiResponse` JSON contract.

## Seeded data

Migration 076 loads the Arden catalogue: 44 duties across Daily Duties (11), Evening Closing (4),
Tuesday (4), Wednesday (14), Thursday (3), Friday (5), Saturday (3). Deliberately **no schedules
and no assignees** — the client decides who performs what.

"Daily duties" appears as the first line of each weekday block on the paper sheet; that is a
pointer to the Daily Duties section rather than a duty of its own, so it is not duplicated.

Two items need attention once assignees are set, because the rule engine cannot express them:

- *"Every other Friday, clean windows inside and out"* — fortnightly. A weekly-Friday rule will
  generate it every week.
- *"After 5 p.m. put out banners by road"* — there is no time-of-day field on a rule.
